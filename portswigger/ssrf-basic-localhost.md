# PortSwigger — Basic SSRF against the local server

**Тип:** SSRF (Server-Side Request Forgery)
**Сложность:** Apprentice
**Лаба:** [PortSwigger Web Security Academy](https://portswigger.net/web-security/ssrf/lab-basic-ssrf-against-localhost)

## Описание

В интернет-магазине есть фича «Check stock» — при клике браузер шлёт запрос с
параметром `stockApi=http://stock.weliketoshop.net:8080/product/stock/check%3FproductId%3D1%3FstoreId%3D1`.
Сервер сам ходит по этому URL. Классическая SSRF: контролируемая сервером исходящая просьба сходить по этому URL. Цель лабы — удалить пользователя `carlos` через админ-панель на
`localhost:8080/admin`.

## Разбор

Фронтенд фильтрует URL с `/admin` — но фильтрация на входе, а не на выходе.
Обходы, которые работают в реальной жизни:

1. **Alternative IP representation**: `127.0.0.1` = `2130706433` = `0x7f000001` =
   `0177.0.0.1`. Парсер URL на сервере может нормализовать иначе, чем фильтр.
2. **URL-кодирование** (двойное тоже): `%61dmin` → `admin`.
3. **Редирект**: если есть открытый redirect на разрешённом хосте, ведём запрос
   через него.

В этой лабе достаточно **двойного URL-кодирования** `/admin`:

```http
POST /product/stock HTTP/1.1
Host: ...

stockApi=http%3A%2F%2F127.0.0.1%3A8080%2F%25%61dmin%2Fdelete%3Fusername%3Dcarlos
```

Размышления: почему двойное кодирование? Сервер декодирует stockApi один раз
(получая URL с `%61dmin`), потом ходит по нему — и парсер пути на внутреннем
сервере декодирует ещё раз. Фильтр смотрел на декодированный один раз вариант,
где `/admin` уже не виден... вернее, виден, если фильтр после первого декода.
В лабе фильтр стоит до декодирования — отсюда и обход.

## Root cause

Сервер делает исходящие запросы по URL, который контролирует пользователь,
без allowlist хостов. Фильтр по подстроке — не защита: представления IP,
кодировки и редиректы ломают его всегда.

## Remediation

- Allowlist: ходить только на явно разрешённые хосты/пути
- Не принимать полный URL от клиента — хранить ID на сервере и мапить в URL
- Запретить редиректы для таких запросов (или перепроверять цель каждого хопа)
- Отдельно: не давать внутренним сервисам отвечать иначе на /admin с localhost

## Что лично я вынес

SSRF — это не «щёлкнуть metadata endpoint в AWS» (хотя 169.254.169.254 —
следующая лаба). Это в первую очередь рассинхрон парсеров URL. Две системы
декодируют одну строку по-разному — вот и уязвимость.
